# 开发难点与解决策略

## 1. 文档定位

本文档用于提前梳理 `深潮回收站` 项目在开发过程中最可能遇到的技术难点、设计难点和演示风险。

它有三个用途：

1. 作为开发前的风险清单
2. 作为开发中的排障参考
3. 作为最终视频和实验报告中的“难点与解决方法”素材

## 2. 难点总览

| 难点 | 典型问题 | 推荐解决方向 |
|---|---|---|
| 游戏循环搭建 | 只能移动，无法形成完整玩法 | 先打通返航结算闭环 |
| 场景切换 | 返航后数据丢失 | 统一用场景管理和结算数据对象 |
| 渲染与逻辑耦合 | 画面能显示但状态混乱 | 更新和绘制分离 |
| 采集交互 | 采集中断和重复采集 | 明确采集状态机 |
| 氧气系统 | 不同帧率下消耗不一致 | 按时间步长计算 |
| 碰撞手感 | 玩家卡墙、穿墙、抖动 | 采用简单稳定的 AABB 修正 |
| 数值平衡 | 返航收益过低或升级太慢 | 前期用保守曲线并多次实测 |
| 数据一致性 | 背包、结算、升级互相污染 | 用独立数据模块和清晰流转 |
| 存档兼容性 | 新增字段后读档失败 | 保留默认值和版本字段 |
| 演示稳定性 | 录视频时临场出错 | 准备专用演示版本 |

## 3. 具体难点拆解

## 3.1 难点一：如何快速做出真正可玩的闭环

### 问题表现

- 有了移动和界面，但没有玩法目标
- 有了采集，但没有返航和结算
- 有了升级，但收益来源不清晰

### 本质原因

项目容易在早期陷入“功能碎片化”，每个部分单独看都有一点，但整体不能玩。

### 推荐解决方法

优先打通最小闭环：

1. 出航
2. 采集
3. 氧气下降
4. 返航
5. 结算

只要这五步成立，项目就从原型进入可玩状态。

### 可用于视频讲解的表达

“开发中最关键的不是先堆更多功能，而是先保证核心闭环跑通。我优先实现了出航、采集、返航和结算，让项目尽快具备可玩性。”

## 3.2 难点二：场景切换时状态怎么保存

### 问题表现

- 游戏场景切换到结算界面时，本次采集数据丢失
- 升级后重新进入游戏，玩家属性没有变化
- 返回基地后海域解锁状态异常

### 本质原因

场景切换不仅是“换界面”，更是“切换数据上下文”。

### 推荐解决方法

- 用 `SceneManager` 统一管理场景切换
- 用专门的数据对象保存“本次出航结果”
- 不要依赖场景销毁前的零散变量

### 可用于视频讲解的表达

“我把场景切换和状态交接分离处理，通过管理器统一传递结算数据和升级数据，避免了换界面后状态丢失的问题。”

## 3.3 难点三：更新逻辑和绘制逻辑容易混在一起

### 问题表现

- 在绘制函数里直接修改玩家数据
- 画面看起来正常，但状态错乱
- 调试时难以判断问题来自逻辑还是渲染

### 推荐解决方法

- `update` 只更新数据
- `paintEvent` 只做绘制
- 所有状态变化统一在更新流程里完成

### 可用于视频讲解的表达

“为了避免渲染和逻辑耦合，我把定时更新和界面绘制分开处理，状态变化统一放在更新循环中完成。”

## 3.4 难点四：采集、背包、结算和升级的数据一致性

### 问题表现

- 采集后背包增加了，但结算没统计到
- 结算已经卖掉了，升级材料还在重复计算
- 升级消耗后，金币没有正确扣除

### 推荐解决方法

- 背包数据只由 `Inventory` 管理
- 结算阶段明确区分“售卖资源”和“保留材料”
- 升级只从统一的玩家资产数据读取

### 可用于视频讲解的表达

“我把资源流转过程拆成背包、结算和升级三个独立阶段，避免同一份数据在不同模块中被重复修改。”

## 3.5 难点五：碰撞手感和移动手感难以兼顾

### 问题表现

- 玩家容易卡墙
- 斜向移动时容易抖动
- 角色贴着障碍物移动手感很差

### 推荐解决方法

- 先使用简单稳定的矩形碰撞
- 水平和垂直方向分开修正
- 暂时不要在前期引入复杂物理系统

### 可用于视频讲解的表达

“为了保证手感和稳定性，我没有一开始就引入复杂物理，而是采用了更容易调试的矩形碰撞和分轴修正方案。”

## 3.6 难点六：氧气系统如何既有压力又不至于太苛刻

### 问题表现

- 氧气掉得太快，玩家来不及体验
- 氧气掉得太慢，游戏没有紧张感

### 推荐解决方法

- 前期先用简单公式
- 允许浅层探索更宽松，深层逐渐加压
- 通过多轮试玩调节基础消耗和深度附加消耗

### 可用于视频讲解的表达

“氧气系统既是限制，也是节奏控制器，所以我把它设计成浅层较宽松、深层更紧张的曲线，而不是全程同一强度。”

## 3.7 难点七：数值设计容易影响演示效果

### 问题表现

- 升级太贵，视频里看不到成长
- 资源价值太低，返航没有成就感

### 推荐解决方法

- 前两次返航就应能买到第一项升级
- 视频演示版本可以略微放宽前期收益，但不要破坏整体逻辑

### 可用于视频讲解的表达

“为了让成长反馈更明显，我把前期收益和升级价格控制在比较容易感知变化的区间，保证短时间演示内也能看到进步。”

## 3.8 难点八：如何让最终视频足够顺畅

### 问题表现

- 项目能运行，但不适合录制
- 实际操作太长，超出视频时长
- 现场演示容易失误

### 推荐解决方法

- 准备专门的演示路线或演示存档
- 控制一次完整出航在 2 分钟左右
- 重要素材先单独录，最后统一剪辑

### 可用于视频讲解的表达

“在开发完成后，我还专门准备了适合视频展示的演示流程，保证能在限定时间内完整体现核心玩法和技术亮点。”

## 4. 开发阶段风险优先级

优先级从高到低建议如下：

1. 核心闭环无法成立
2. 场景切换状态丢失
3. 采集和结算数据错乱
4. 碰撞和移动手感差
5. 数值节奏不合理
6. 存档和图鉴问题
7. 演示素材不足

## 5. 最务实的解决原则

如果时间紧，始终坚持：

1. 先解决“能不能玩”
2. 再解决“好不好玩”
3. 最后解决“好不好看”

## 6. 结论

大作业最怕的不是技术点少，而是系统很多但没有闭环。  
只要提前识别这些难点，并且按闭环优先、状态清晰、模块独立的方式推进，项目就能稳定落地，也更方便在最终视频里讲清楚自己的工作量和技术价值。
