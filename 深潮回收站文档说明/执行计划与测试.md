# 执行计划与测试

本文档把《项目工作流程.md》中的阶段目标进一步落成执行步骤、测试动作、边界检查、回归清单和通过标准。

重点原则是：每个阶段都要回答三件事。

1. 具体要怎么完成。
2. 完成后要怎么验证。
3. 出问题时先查什么。

## 总测试策略

- 优先保障主路径，再覆盖异常路径，最后做长时间和演示场景验证。
- 测试分为阶段内自测、跨阶段联调、完整出航回归、最终演示复测四层。
- 每加入一个系统，都要复测启动、移动、碰撞、氧气、采集、返航、结算主链路。
- 如果某阶段测试无法稳定复现，优先补日志和调试开关，而不是盲改。
- 测试结论必须能写成一句明确判断，例如“通过”“失败”“需继续观察”。

## 测试记录模板

- 测试编号：建议使用 阶段编号 + 序号，例如 P4-03。
- 测试目标：写清楚要验证的单个结论。
- 前置条件：包括海域、升级等级、背包状态、调试开关。
- 操作步骤：不要省略关键输入和移动路线。
- 预期结果：写清楚数字、状态或界面变化。
- 实际结果：如果失败，必须记录观察到的异常现象。
- 初步判断：是逻辑错误、表现错误还是数据同步错误。
- 回归要求：修完后至少重跑哪几条旧用例。

### 常见失败模式与排查顺序

- 失败模式：把渲染、输入、资源加载全塞进 main 函数。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。
- 失败模式：依赖绝对路径读取素材。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。
- 失败模式：在还没形成固定刷新入口前就堆玩法逻辑。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。
- 失败模式：没有记录启动问题，导致环境变化后重复踩坑。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。

### 常见失败模式与排查顺序

- 失败模式：最后阶段只顾录视频，不回归主程序。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。
- 失败模式：文档和实际实现脱节。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。
- 失败模式：仓库里混入无关文件。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。
- 失败模式：没有预留重新录制和导出的时间。
排查顺序：先确认数据有没有变，再确认状态有没有被正确读取，最后确认只是界面没显示还是逻辑没执行。

## 最终演示前完整回归

1. 从开始界面进入基地，再出航到海域。
2. 完成一次采集并观察背包变化。
3. 触发低氧预警并安全返航。
4. 进入结算界面并确认金币变化。
5. 购买至少一项升级并再次出航验证效果。
6. 展示至少一个危险机制和一个海域差异点。
7. 退出后重进，确认存档仍然正确。
8. 按视频脚本完整讲一遍，确认口径和画面一致。
